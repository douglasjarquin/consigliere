Status: **closed, unconditional approval.** Round 1 of the `omo:reviewer` verification-gate loop rejected the initial submission with seven real, reproduced blocking defects; round 2 confirmed all seven held under adversarial re-testing, then found four more (one of them, B4's underlying class, only partially closed by round 1) plus three documentation defects; round 3 confirmed all eleven prior findings held, then found two more blocking defects -- one a regression introduced by round 2's own fix for BL-2, the other a fourth instance of the B4/BL-1 abandonment-path class -- plus three further documentation defects. Round 4 independently re-verified all thirteen prior findings hold (including reproducing the live daemon-kill scenario, a full boundary/stress sweep of the round-3 control-channel fix, and an exhaustive multi-path/multi-index manifest-write-failure matrix), found nothing new, and returned unconditional approval. An independent fable-model review then found two further real items (the daemonize escape and unsynchronized control-channel writes); the write-serialization fix held on first submission, but the daemonize-escape fix took eleven more post-closure verification-gate rounds, and is not fully closed: round 1 rejected the first (single-snapshot) attempt with five real findings (see "Post-closure verification-gate round 1" below); round 2 rejected the corrected (continuous-tracking) design's own first implementation with five more real findings, all in the tracking mechanism itself rather than the underlying design (see "Post-closure verification-gate round 2" below); round 3 confirmed every prior finding held, then found two more blocking defects in that round's own fixes -- a timeout that did not actually bound its call in every case, and a fix with no regression test (see "Post-closure verification-gate round 3" below); round 4 confirmed round 3's fixes held, fixed one more real, cheaply-closable gap in the tracking mechanics, and found the daemonize-escape item's "fixed" framing had been overstated -- the classic double-fork daemonize idiom evades process-tree polling in a way that is a structural limit of this mechanism, not a further bug, and is now disclosed as a genuinely open limitation rather than fixed (see "Post-closure verification-gate round 4" below); round 5 confirmed rounds 1-4 held and the double-fork disclosure's reproduction numbers were accurate, then found round 4's own two fixes were each incomplete in a way that reopened exactly the class of bug they were meant to close -- the descendant-kill sequence stopped tracking before its own multi-second kill window ran, and every previously-seen pid had become a permanent, never-revalidated polling root -- both now fixed for real (see "Post-closure verification-gate round 5" below); round 9 confirmed the code holds a third consecutive time via its own from-scratch re-derivation (not trusting round 8's wording), tested a multi-poll relay chain, a triple-fork, and orphan reparenting, and found round 8's own commit had repeated the exact off-by-one round-count mistake it was correcting plus stated the chain condition slightly too narrowly (see "Post-closure verification-gate round 9" below); round 10 confirmed the code holds a fourth consecutive time, found the same round-count arithmetic slip recurring a third time, and found round 9's own corrective clause ("what cannot happen is catching links piecemeal across separate polls") was itself falsified by the exact relay case round 9 had confirmed works -- corrected to state the real mechanism, where a single never-caught link (not "piecemeal" discovery, which is the normal case) is what permanently breaks discoverability (see "Post-closure verification-gate round 10" below); round 11 confirmed the code holds a fifth consecutive time, then found round 10's own restatement was itself still wrong -- it required each link to be individually caught while its own parent was already, separately, tracked, when a single poll can in fact catch several brand-new generations at once (reproduced: three generations discovered in one single, first-ever poll) -- corrected to the combined single-poll-or-incremental condition (see "Post-closure verification-gate round 11" below). This document was updated with the honest round-by-round outcome throughout, per this project's established practice (see `docs/spikes/spike-b-results.md`), rather than rewritten to hide any rejection.

This spike proves that a real, external, daemon-independent OS process (`cs-runner`, written in Go) survives a `kill -9` of the entire Elixir daemon, detects that death on its own (via control-channel EOF, no daemon-side cooperation), terminates the harness process group it owns, verifies that termination at the OS level, and leaves a truthful manifest behind -- and that a reconciler function reading that manifest after the fact reaches the correct classification, per `docs/phase0-report.md` section 15's Spike C design and `docs/protocols/runner.md`.

## What was built

- `runner/cs-runner/` (Go): a standalone runner binary, independent of the Elixir daemon's own lifetime.
  - `manifest.go`: crash-safe manifest read/write (temp file + fsync + atomic rename + directory fsync), matching `docs/protocols/runner.md`'s schema.
  - `spawn.go`: spawns the harness as its own session/process-group leader (`Setsid: true`) and blocks until the child's own `setsid()` call is confirmed via `Getpgid` before returning -- closing a real startup race (see "Two real races found" below). If that confirmation window elapses first, the already-started child is cleaned up with a specific-pid signal (not a pgid broadcast, since the group cannot yet be trusted) before the error is returned, rather than left running with no handle anyone could use to find it (round 2, finding BL-1).
  - `termination.go`: the SIGTERM / bounded-wait / SIGKILL / bounded-verify sequence from `docs/protocols/runner.md`'s "Termination sequence" section, verifying death via `kill(-pgid, 0)`, never by trusting `Wait()` alone. `checkProcessGroupFn`/`sendSignal` are package-level seams distinguishing three liveness outcomes (`groupGone`/`groupAlive`/`groupUnknown`, the last covering EPERM and any other unexpected error) so an unverifiable check can never be misread as "confirmed gone" (round 1, finding B2), and `Terminate` refuses pgid values of 0, 1, or negative outright, since `kill(-0, ...)`/`kill(-1, ...)` are POSIX broadcast signals rather than a specific group (round 1, finding B6). `TerminateGroupAndDescendants` (post-closure fix, see below) additionally reaches any descendant that has escaped the harness's process group entirely via its own `setsid()` call, which `Terminate` alone structurally cannot.
  - `processtree.go` (post-closure fix, new): walks the real OS process tree from a single `ps -axo pid=,ppid=,lstart=` snapshot to find every transitive descendant of a given pid, regardless of process group membership, capturing each process's start time alongside its pid so a later termination can revalidate it is still the same process before signaling it.
  - `control.go`: the runner-as-server NDJSON Unix-domain-socket control channel. `ReadLoop`'s EOF path is the entire daemon-independence mechanism: a `kill -9` of the daemon closes every file descriptor it held, including its end of this socket, which surfaces here as an ordinary read EOF with zero daemon-side cooperation required. Reads via `readBoundedLine`, a hand-rolled `bufio.Reader.ReadSlice`-based reader bounded to 16MiB (`maxControlLineBytes`) that, unlike `bufio.Scanner`, can resume after a too-long line instead of dying permanently: a line past the bound is drained up to its terminating `\n` and skipped (reported as `errLineTooLong`), and the loop keeps reading -- neither the 64KiB `bufio.Scanner` default (round 1, finding B3) nor an unbounded reader (round 1's fix for B3 removed the cap entirely, letting an unterminated write grow memory without limit -- round 2, finding BL-2) nor a *bounded* `bufio.Scanner` (round 2's own fix for BL-2 correctly bounded memory but, because `Scan()` can never be resumed once it returns false due to an error, permanently stopped reading the channel after one too-long line -- silently disabling daemon-death detection for the rest of the Attempt -- round 3, finding BLOCK-1) survive all three requirements at once. `onEOF` fires only for a genuine read error (a real disconnect), never for `errLineTooLong`. `Send` (post-closure fix, see below) holds its mutex across the entire write, not just the `conn` field read, so concurrent callers can never interleave mid-syscall.
  - `main.go`: wires the full lifecycle -- write `starting` manifest, spawn harness (reaping it via a background goroutine started immediately on spawn, not after control-channel setup -- round 1's zombie-vs-EPERM finding, below, made this ordering load-bearing), write `running` manifest, accept the daemon's control connection, race the harness's own exit against a control-channel-triggered termination (`cancel` message or EOF), run the termination sequence if triggered, write the final `dead_verified`/`dead_unverified` manifest, send `termination_complete`, exit. A shared `terminateAndFinalize` helper (wrapped by `terminateAndReport`, which logs rather than discards a final-manifest write failure -- round 2, finding BL-4) runs the termination sequence and writes the resulting terminal manifest state from every path that can end a runner's life: a natural harness exit that may still leave stragglers in the group (round 1, finding B1), and four previously-unhandled post-spawn failure paths that used to abandon an already-running harness -- control-channel bind failure, the daemon never connecting (round 1, finding B4), the running-manifest write itself failing (round 2, finding BL-1, via the `writeManifestFn` seam), and the *terminating*-manifest write failing on the cancel/EOF path (round 3, finding BLOCK-2 -- the one `writeManifestFn` call site round 2 left unguarded). A harness killed by a signal is now reported as such (`signaled: true` in both the `harness_exited` message and the manifest), rather than the field being hardcoded `false` with an uninformative `-1` exit code (round 2, finding BL-3).
- `daemon/lib/consigliere/runner_launcher.ex` (Elixir): the daemon-side half of the protocol for this spike -- `Port.open/2`-spawns `cs-runner`, connects to its control socket as a `:gen_tcp` `{:local, path}` client, and exposes `launch/1`, `cancel/1`, `recv/2`. Deliberately minimal and not a supervised OTP process: it exists to prove the protocol boundary, not to be the real production launcher (that belongs to Phase 1/2, once `RunnerProcess` from Spike B is rebuilt on top of `cs-runner` instead of a plain Port-spawned fake harness).
- `daemon/lib/consigliere/reconciler.ex` (Elixir): `Reconciler.classify/1` reads a manifest file from disk and classifies it per `docs/protocols/runner.md`'s "Restart and reconciliation contract": `dead_verified` -> `:lost`; `dead_unverified` -> `:quarantine_incident`; any non-terminal state (`starting`/`running`/`terminating`) with a valid pgid (an integer greater than 1; anything else, including a missing pgid or 0/1/negative, quarantines outright rather than ever reaching a liveness check -- round 1, finding B6) -> a real OS-level process-group liveness check (`kill -0 -<pgid>`) decides between `:adopt_and_kill` (group still alive, or unverifiable) and `:lost` (conclusively gone); anything unparseable or unrecognized -> `:quarantine_incident` with `:corrupt`, never a crash. `kill_result_alive?/1` distinguishes an explicit "No such process" (conclusively gone) from any other failure output, in particular "Operation not permitted"/EPERM, which is treated as unverifiable rather than gone -- reusing a workspace under a live process is the unsafe direction (round 1, finding B2). This spike deliberately does not cross-reference a real Attempt row or touch SQLite -- there is no Mission/Attempt/Workspace schema in this spike's scope, only the classification function itself.
- `daemon/spike_scripts/spike_c_driver.exs`: the live tmux/OS-level demonstration script for the daemon-kill invariant, analogous to Spike B's `coordinator_independence_driver.exs`.

## Two real races found (not assumed, reproduced and fixed)

1. **`setsid()` startup TOCTOU**: `cmd.Start()` returns to the parent as soon as `fork()` completes; the child's own `setsid()` call happens asynchronously afterward. An immediate `kill(-pgid, 0)` check (or, worse, the real termination sequence) executed in that window can silently miss the child, because the process group it actually joins isn't confirmed yet. Found via a genuinely failing `termination_test.go` run, not assumed. Fixed by removing `Terminate`'s racy "already dead" fast path entirely, and by having `SpawnHarness` poll `Getpgid(pid) == pid` before returning a `HarnessHandle` to any caller -- the same fix applied at the real call site (`main.go`), not just in the test helper.
2. **Shell `trap` installation timing**: even after fixing race 1, a test harness that installs `trap '' TERM` to ignore SIGTERM (to exercise the SIGKILL escalation path) still failed intermittently, because the shell needs time to actually execute the `trap` builtin before a signal sent immediately afterward is honored against that new disposition -- sending it too early kills the shell via the *default* disposition instead, never reaching the SIGKILL path the test meant to exercise. Fixed with a real synchronization marker (the shell `touch`es a ready-file immediately after the `trap` statement; the test polls for that file) instead of an arbitrary `sleep`, which would have been nondeterministic.

## A real OS constraint found: socket path length

macOS's `sockaddr_un.sun_path` limit (~104 bytes) caused `bind: invalid argument` when a control-socket path was built under `t.TempDir()`'s long, deeply nested per-test directories. Fixed with short paths directly under `/tmp` (a `shortSocketDir(t)` helper in Go tests, `/tmp/csc-*` directories in Elixir tests and the driver script) -- and this is exactly why the real runner protocol's production path (`/var/run/csd/attempts/<attempt_id>/`) is deliberately short rather than nested under a long project-specific prefix.

## Results by criterion

Numbering follows `docs/phase0-report.md` section 15's Spike C list.

1-2. **Start a harness through the external runner; `kill -9` the entire daemon process.** Proven live via `daemon/spike_scripts/spike_c_driver.exs` run under `mix run` inside a tmux pane, killed from a separate shell with `kill -9 <daemon OS pid>`. Also covered automatically (without needing a literal whole-BEAM kill) by `daemon/test/consigliere/runner_launcher_test.exs`'s third test, which closes the daemon's end of the control-channel socket directly -- the identical mechanism `kill -9` triggers at the kernel level (fd closure), per `control.go`'s own documented invariant.
3. **Runner observes control-channel EOF, independent of daemon shutdown logic.** Confirmed both live (see below) and in the automated test: `termination_reason` in the final manifest and in the `termination_complete` message is `"control_eof"`, distinct from the explicit `"cancel"` path also covered by the same test file.
4. **Graceful-term/bounded-wait/hard-kill sequence, verified conclusively.** `termination.go`'s `Terminate/3` implements exactly this sequence. Verification is via `kill(-pgid, 0)`, not an actual `/proc`/`kinfo_proc` process-table scan (`docs/protocols/runner.md`'s own wording allows either; this spike used the former) -- round 1 of the verification gate found this distinction matters in one specific way: `kill(-pgid, 0)` returning an error other than ESRCH (in particular EPERM) must be treated as "cannot verify," never as "confirmed gone" (see round 1, finding B2, below). With that fix, and after also discovering that verification requires the process to actually be reaped by its parent (round 1's zombie-vs-EPERM finding, below), the harness's exit is confirmed genuinely gone, not merely that `Wait()` returned (round 1, finding B1) or that a single check happened to return without error.
5-7. **Restart the daemon; reconciler classifies the dead Attempt as lost; workspace state left evaluable, not ambiguous.** This spike has no real daemon-restart/boot sequence, Mission/Attempt schema, or Workspace entity to restart or reconcile against -- that is explicitly out of scope here (see `docs/phase0-report.md`'s Spike A/B precedent of proving mechanisms in isolation before Phase 1 wires them into the real schema). What this spike proves instead is the classification function itself: `Consigliere.Reconciler.classify/1`, tested in `daemon/test/consigliere/reconciler_test.exs` against (a) a real manifest produced by an actual `cs-runner` run through the cancel path (`:lost`), (b) a real still-running `cs-runner` process checked via a genuine OS-level process-group scan (`:adopt_and_kill`), (c) a forced `dead_unverified` manifest (`:quarantine_incident`), and (d) a manifest claiming `running` against a process group that is actually dead, using the same real `kill -0 -<pgid>` mechanism the production reconciler would use, not the manifest's own self-report (`:lost`, per the protocol's "verify independently" rule).
8. **Exit criterion.** Live evidence below shows zero processes surviving the kill, confirmed from outside the killed daemon by direct `ps`/`kill -0` inspection, plus the manifest's own `dead_verified`/`control_eof` record -- both independently pointing at the same conclusion, neither trusting the daemon's own report (there is no daemon left to report anything).

## Verification-gate round 1: rejection, and what it caught

A strict adversarial review (`omo:reviewer`) reproduced the live daemon-kill scenario itself (confirming the headline claim is real, and stronger than this document originally claimed -- it also exercised a `trap '' TERM` harness end-to-end through the full 5s graceful window before SIGKILL escalation, which round 0 had not done) and rejected the submission with seven blocking findings, four of them reproduced live. All seven are fixed below, each with a new RED-then-GREEN test.

1. **B1 (fixed): natural harness exit wrote `dead_verified` with zero verification, orphaning any child the harness backgrounded before exiting.** `main.go`'s natural-exit branch wrote `dead_verified` the instant `Cmd.Wait()` returned, with no check that the process group was actually empty. Reproduced with a harness that backgrounds a child and exits immediately (`(sleep 30 &); exit 0`): the manifest said `dead_verified` while a live grandchild remained in the same pgid. **Fixed**: the natural-exit branch now runs the same `Terminate` sequence against the group before declaring a terminal state, via the shared `terminateAndFinalize` helper. New test: `TestRun_NaturalHarnessExitReapsSurvivingGroupMembers`, RED (grandchild still alive, `kill(-pgid,0)` returned no error) then GREEN (group conclusively empty, `kill(-pgid,0)` returns `ESRCH`).
2. **B2 (fixed): `EPERM` was misread as "gone," producing a false `dead_verified`/`:lost`.** `pgidHasMember` (Go) and `process_group_alive?` (Elixir) both treated any error from the liveness check, including `EPERM` (the exact "process the runner cannot signal due to a permissions change" case `docs/protocols/runner.md:125` names), as "no member." **Fixed** on both sides: Go's `checkProcessGroupFn` now distinguishes `groupGone` (`ESRCH`) from `groupUnknown` (anything else), and `waitUntilGone` only resolves `true` on `groupGone`; Elixir's `kill_result_alive?/1` only reads an explicit "No such process" as gone, defaulting to "alive" for anything else including "Operation not permitted." New tests: `TestTerminate_UnverifiableGroupReportsUnverifiedRatherThanAssumingGone` (Go, via injectable `checkProcessGroupFn`/`sendSignal` seams, since a real `EPERM` needs privileges this suite cannot assume) and four `kill_result_alive?/1` cases (Elixir), all RED (symbols/behavior didn't exist) then GREEN.
   - **A second-order discovery while fixing this**: correctly distinguishing `EPERM` from `ESRCH` exposed a real, previously-masked macOS behavior -- `kill(-pgid, 0)` against a process group whose leader has exited but not yet been *reaped by its own parent* returns `EPERM`, not `ESRCH`, until the parent calls `Wait()`. The old (buggy) code silently treated this the same as "gone," so `TestTerminate_CooperativeProcessExitsOnSIGTERM` and `TestTerminate_StubbornProcessRequiresSIGKILL` had been passing for the wrong reason the whole time (their `defer cmd.Wait()` reaped too late to matter to the assertions). Once B2's fix correctly refused to treat `EPERM` as "gone," these two tests started failing for real, revealing the masked bug. **Fixed** by reaping concurrently in both tests (`go cmd.Wait()` instead of a deferred one) -- exactly matching `main.go`'s real production pattern, which already starts its own reaping goroutine the moment the harness is spawned (moved earlier in this diff specifically because of this finding, since the two new B4 failure paths below had no reaper running yet either).
3. **B3 (fixed): any control-channel read error was treated as "the daemon died," including a message merely too large for `bufio.Scanner`'s default 64KiB token limit.** Reproduced: a single valid 70,000-byte NDJSON line (no embedded newline) was misread as a scan error, triggering the same `onEOF` path a real daemon death does -- killing a live harness over a message that was never actually a disconnection. **Fixed** by switching `ReadLoop` from `bufio.Scanner` to `bufio.Reader.ReadString`, which has no fixed line-length cap. New test: `TestControlChannel_ReadLoopHandlesOversizedSingleLineMessage`, RED (message never delivered, timeout) then GREEN (delivered intact, no false EOF).
4. **B4 (fixed): a post-spawn failure (control-socket bind failure, or the daemon never connecting) abandoned an already-running harness, leaving the manifest stuck at `running` forever.** Reproduced both ways: an unbindable control-socket path (long enough to exceed `sockaddr_un.sun_path`), and no client ever connecting within the accept window. In both cases the harness kept running with no record that anything had gone wrong. **Fixed**: both failure branches now call `terminateAndFinalize` before returning their error, terminating the harness and writing a terminal manifest state (`termination_reason` of `"control_channel_setup_failed"` or `"daemon_never_connected"`). New tests: `TestRun_ControlSocketBindFailureTerminatesAlreadySpawnedHarness` and `TestRun_AcceptTimeoutTerminatesAlreadySpawnedHarness` (the latter via a new `runWithAcceptTimeout` that `run` wraps with the real 30s production timeout, keeping the test fast), both RED then GREEN.
5. **B5 (fixed): the `dead_unverified` path was never produced or tested anywhere in the codebase, despite being the trigger for invariant #6's workspace quarantine.** **Fixed**: `TestRun_UnverifiableTerminationWritesDeadUnverified` exercises the full `run()` lifecycle against a genuinely running harness, with the liveness check stubbed to report `groupUnknown` (simulating an unverifiable case no privilege level in this test environment can produce for real), asserting `cs-runner` itself writes `dead_unverified` -- not merely that `Terminate` can return `verified=false` in isolation. The Elixir side already had a forced `dead_unverified` manifest case from round 0; this closes the Go-side gap.
6. **B6 (fixed): neither `Terminate` nor the reconciler guarded against degenerate pgids (missing, 0, 1, negative).** `kill(-0, ...)` and `kill(-1, ...)` are POSIX broadcast signals, not a specific process group. Reproduced with a verbatim copy of `Terminate` run against pgid 0 in a fresh session with an innocent bystander process in the same group: the bystander was killed. **Fixed**: `Terminate` now refuses any pgid `<= 1` outright, returning an error without signaling anything; `Reconciler.classify_manifest/2` quarantines (never `:adopt_and_kill` or `:lost`) whenever the manifest's pgid is missing or not a valid integer greater than 1, before ever consulting a liveness check. New tests on both sides, including `TestTerminate_RefusesDegeneratePgidWithoutSignalingCallersOwnGroup`, which spawns a real innocent bystander process group and asserts it survives calls with pgid 0, 1, and -5.
7. **B7 (fixed, documentation-only): overclaimed criterion-4 wording, and three omitted protocol responsibilities not disclosed.** This document's criterion-4 line claimed process-table inspection when the actual mechanism is `kill(-pgid, 0)` (both are permitted by `docs/protocols/runner.md`, but the document should say which one was built) -- corrected above. Three of `docs/protocols/runner.md`'s nine runner responsibilities are not implemented in this spike and were not previously disclosed: responsibility 5 (framing and forwarding the harness's stdout/stderr over the control channel), responsibility 8 (rejecting any control-channel command carrying a stale `fencing_token` -- reproduced: a `cancel` with an arbitrary wrong `attempt_id`/stale `fencing_token` from any socket client kills the harness today, since nothing checks either field), and responsibility 9 (a local status query). All three are now named explicitly in Known Limitations below, and this diff's own premature "done and passing" framing in `docs/phase0-report.md`'s checklist has been reverted pending this gate's actual close.

## Verification-gate round 2: rejection, four more findings plus three documentation defects

A second adversarial review reproduced the live daemon-kill scenario again (confirmed it still works after round 1's fixes) and independently re-verified all seven round-1 fixes hold under further adversarial testing (multiple straggler shapes for B1, a real root-owned-process EPERM for B2, back-to-back oversized-and-malformed frames for B3, both B4 paths, B5's non-vacuousness, B6's guard, and B7's disclosures) -- **none of that work needed to be redone.** It then found four new blocking defects and three documentation defects, one of them (BL-1) a second instance of round 1's own B4 class that round 1 had only partially closed.

1. **BL-1 (fixed): two more post-spawn abandonment paths, one of them worse than anything round 1 fixed.** (a) If `WriteManifest` for the *running* manifest itself fails (a transient disk/permissions fault) after the harness is already spawned, the harness was abandoned with **no manifest ever recording its pgid at all** -- worse than round 1's B4 cases, since nothing downstream could ever find the orphan (reproduced live: a `chmod 500` on the manifest directory mid-write left a `sleep 300` reparented to init forever, undiscoverable). (b) If `SpawnHarness`'s own confirmation window (`spawn.go`) elapses before `setsid()` is observed, the already-started child was left running with no handle returned to anyone. **Fixed**: the running-manifest write now goes through `terminateAndReport` on failure (same shared helper the two round-1 paths use, via the new `writeManifestFn` seam so a test can force exactly this write to fail); `SpawnHarness` now cleans up the orphaned child itself (a specific-pid signal, not a pgid broadcast, since the group cannot yet be trusted) and still returns its pid so a caller can verify the cleanup. ## Known limitations carried forward (not silently accepted)

- No real daemon boot/restart sequence, Mission/Attempt schema, or Workspace entity exists in this spike; `Consigliere.Reconciler.classify/1` proves the classification logic in isolation, matching this project's Spike A/B precedent of proving mechanisms before Phase 1 wires them into the real schema. Phase 1/2 must wire this into an actual `Csd.Reconciler` boot-time scan over `runners/<attempt_id>/manifest.json` files, cross-referenced against real Attempt rows, per `docs/protocols/runner.md`'s full restart contract (steps 2, 3, and 6 of that contract -- Attempt-row cross-reference, checkpoint-vs-lost distinction, and manifest archival -- are explicitly not built here).
- `daemon/lib/consigliere/runner_launcher.ex` is a spike-scoped helper, not a supervised OTP process. Phase 1/2's real launcher must be a proper supervised child (mirroring Spike B's `RunnerProcess`) that owns the `Port`/socket for the life of a real Attempt, not a bare struct returned from a function call.
- Three of `docs/protocols/runner.md`'s nine numbered runner responsibilities are not implemented here (round 1, finding B7): responsibility 5 (stdout/stderr framing and forwarding over the control channel), responsibility 8 (rejecting a stale `fencing_token` -- today, any socket client's `cancel` is honored regardless of `attempt_id` or `fencing_token`, since the single-accepted-client design was assumed sufficient for this spike's scope but is not itself a fencing mechanism), and responsibility 9 (a local status query). Phase 1/2 must implement all three before this runner is used against a real Attempt.
- `control.go`'s `NewControlChannel` unconditionally removes any existing file at the socket path, so a second runner instance can silently steal a live runner's socket. No lock or ownership check exists yet; `docs/protocols/runner.md:114` anticipates this hazard but this spike does not close it.
- `Reconciler.classify/1` does not consult `runner_pid` at all, though `docs/protocols/runner.md:137` gates the pgid liveness check on `runner_pid` being absent from the process table first. Today a perfectly healthy live runner always classifies as `:adopt_and_kill` after a simulated daemon restart, which happens to be safe (adopt-and-kill on an already-fine runner is a no-op death sentence for nothing that needed killing) but is not the protocol's actual decision procedure.
- A manifest's `pgid` could, in principle, have been recycled by the OS to an unrelated process group between the manifest being written and being read back (e.g. after a long daemon outage). Neither `Terminate` nor `Reconciler` detects this; both would act against whatever currently holds that pgid. Low probability in practice, and no evidence of it occurring in any test or live run here, but it is the one remaining way a valid-looking pgid could cause `Terminate`/`Reconciler` to signal or judge the wrong process group despite round 2's degenerate-pgid guard (finding B6) working exactly as designed.
- The 5-second graceful-wait / 2-second verify timeout budget from `docs/protocols/runner.md` was exercised against both a cooperative and a `trap '' TERM`-stubborn harness at the Go unit level, via the live daemon-kill demonstration, and (round 4) end-to-end through the Elixir launcher (`runner_launcher.ex`) against a `trap '' TERM` harness specifically: both runner and harness were confirmed still alive at t+2s (mid-graceful-window), both gone by t+10s, and the manifest's `verified_dead_at` timestamp landed ~5.05s after the kill -- the full graceful window followed by SIGKILL escalation, exactly as designed. That single 7-second figure (5s + 2s) is no longer the worst-case total, though: since the daemonize-escape fix, `TerminateGroupAndDescendants` runs the group phase and the descendant phase sequentially, each with its own full 5s/2s budget, so a harness group that needs the full escalation *and* has a stubborn tracked descendant that also needs it can take up to roughly 14 seconds end to end, not 7. An eighth post-closure verification-gate round measured this live against exactly that combination (a `trap '' TERM` in-group straggler plus a SIGTERM-ignoring `setsid()` escapee) at ~10.1 seconds from EOF to runner exit. `docs/protocols/runner.md`'s 5s/2s figure describes each phase's own budget correctly; it does not currently state that a runner with both a group-scoped and a descendant-scoped target to kill can take the sum of both (post-closure fix, disclosed not fixed -- serializing the two phases, rather than running them concurrently, was a deliberate choice earlier in this document to keep the descendant-tracking snapshot simple and correct, and remains the right tradeoff for a Phase 0 spike, but the resulting wall-clock bound should be stated explicitly wherever `docs/protocols/runner.md`'s figure is quoted as an operator-facing guarantee).
- `terminateAndFinalize` discards `TerminateGroupAndDescendants`'s own returned error (as opposed to the manifest-write error, which `terminateAndReport` does surface) -- since the post-closure daemonize-escape fix, this is `errors.Join` of both the group phase's and the descendant phase's errors, so a descendant-signal or pid-revalidation failure is now also silently lost alongside the original group-phase error; confirmed live this is currently safe (`verified` is computed independently of `err` and still correctly reflects the true outcome, e.g. a real `EPERM` group still correctly yields `dead_unverified`), but the underlying error itself -- which would explain *why* verification failed -- is lost with no diagnostic (round 3 finding, disclosed not fixed; widened by the post-closure fix, still disclosed not fixed).
- `main.go`'s `sha256File(execPath)` error is silently discarded (`execHash, _ := sha256File(execPath)`); if hashing fails (e.g. the harness is invoked by bare name via `PATH` lookup rather than a resolved path), the manifest records an empty `harness_executable_sha256` with no signal, defeating responsibility 4's swapped-binary detection precisely when it can't verify anything (round 3 finding, disclosed not fixed).
- `terminateAndReport`'s stderr diagnostic is unrecoverable in the two situations where it matters most: in the `control_eof` case the daemon (the only plausible reader of this process's stderr) is already dead; in a sustained-fault case (e.g. a full disk) the same fault that broke the first manifest write will likely break the recovery write too, so the log line may never reach any durable destination either (round 3 finding, disclosed not fixed; the underlying termination behavior remains safe in both cases -- the harness is still killed).
- `writeManifestFn`, `checkProcessGroupFn`, `sendSignal`, and `currentStartedAtFn` are unsynchronized package-level test seams; every test today restores them via `t.Cleanup`/`defer` and none use `t.Parallel()`, so there is no present data race (`go test -race -count=2` and `-shuffle=on` are clean), but nothing enforces this going forward (round 3 finding, disclosed not fixed; a fourth post-closure round found this bullet had only been updated in the round-2 narrative and not here -- corrected).
- `daemon/spike_scripts/spike_c_driver.exs` does not clean up `/tmp/csc-tmux-driver` after the daemon is killed (the process that would run the cleanup is itself the one being killed); cosmetic, no invariant depends on it (round 3 finding, disclosed not fixed).
- `readBoundedLine` never returns partial data alongside an error, so an unterminated final line (no trailing `\n`) sent immediately before the connection closes is dropped rather than delivered; the resulting `onEOF` still runs the identical termination sequence, so this has no effect on any invariant this spike proves, and `RunnerLauncher.send_json/2` (the one production sender in this spike) always appends `\n` (round 4 finding, disclosed not fixed).
- **The descendant tracker's guarantee is "caught within one poll interval," not "caught instantly," and that interval starts slightly later than the harness's own spawn.** A descendant that is forked and has its parent (the harness) die and get reaped within less than one `descendantPollInterval` (150ms in production) can still be missed -- polling at any finite frequency has this residual window, and shrinking the interval further only shrinks the window, it cannot close it to zero. A second post-closure verification-gate round found this window is not purely the poll interval: `main.go` now hashes the harness executable (`sha256File`) before the tracker starts (moved there to fix a separate abandonment-path defect), and that hash's cost scales with the executable's size -- measured at well under the poll interval for small binaries, but potentially exceeding it for a large real coding-harness binary. This is a fundamentally different, much narrower gap than the one this fix closes (which was: any delay at all, up to and including the harness's entire remaining lifetime after spawning the descendant, guaranteed a miss). A miss of this kind is indistinguishable, from the tracker's point of view, from "there never was a descendant" -- no poll ever errored, so `TerminateGroupAndDescendants` still reports `verified=true`/`dead_verified` even though the missed escapee is, in fact, still alive. Not fixed, and not closable without a fundamentally different mechanism (e.g. a kernel-level process-exit notification), which is out of scope for a Phase 0 spike (post-closure fix, disclosed not fixed).
- **The descendant tracker's pid-reuse risk is mitigated, not eliminated.** A second post-closure verification-gate round found the original "widens but doesn't newly introduce" framing understated the actual risk (measured pid churn on a real machine was fast enough that a long-running harness's tracked pid list could plausibly go stale within its own lifetime) and found the descendant-kill path signaled every tracked pid unconditionally, with nothing checking it was still the same process. A fifth post-closure round found the mitigation that followed had a real gap of its own: every *previously-seen pid* had also been made a permanent, never-revalidated polling root (round 4's fix for a different bug), so a pid recycled by the OS could sweep an unrelated process's real children into the tracked set -- reproduced against the real termination path, an unrelated process's child got signaled. **Fixed**: `descendantsOfAny` now revalidates every root with a recorded identity (every previously-seen pid) against the same snapshot it uses for traversal, before ever traversing from it, and the tracker prunes any that no longer match; `terminateTrackedDescendants` additionally revalidates each candidate pid against a fresh snapshot at the moment it is first signaled in a given phase. A pid that no longer matches (exited, or recycled to something else) is never traversed from, never signaled, and never waited on. The residual window this leaves is bounded to the gap between a pid's most recent revalidation and the moment it is actually signaled -- at most one poll interval -- and is now the same order of magnitude as the pre-existing pgid-reuse limitation above, not larger. Two narrower gaps remain disclosed and not fixed: `ps`'s own `lstart` rendering has one-second granularity, so a pid recycled by an unrelated process within the same wall-clock second would pass revalidation undetected; and the harness's own top-level root pid (as opposed to every pid discovered beneath it, which is now revalidated) is still never revalidated -- it is polled again and again for as long as the tracker runs, including throughout the termination sequence, with no check that it still refers to the same harness process rather than something the OS has since recycled that exact pid to.
- **The classic double-fork daemonize idiom is not closed by this fix, and cannot practically be closed by process-tree polling at all.** The fix closes any escape whose process-tree link back to the harness survives at least one poll interval (a harness that directly backgrounds a `setsid()` process, for example). The standard daemonize idiom is different: an *intermediate* process forks, calls `setsid()`, forks the process that actually survives, and exits immediately -- typically within about a millisecond, since it does nothing else. If that intermediate dies before any poll observes it, its child was never a discoverable descendant of the harness at all: by the very next poll, the child has already been reparented to init with no process-tree link connecting it back. This is not the sub-poll-interval timing race described above, which a faster interval would narrow -- no realistic polling frequency can help here, since spawning `ps` itself costs tens of milliseconds while the intermediate's real lifetime is on the order of a millisecond. A fourth post-closure verification-gate round reproduced this end to end through `run()`'s real control-channel-EOF path with the real binary: 14 of 18 iterations left a double-fork daemon alive while the manifest reported `dead_verified`. A seventh post-closure round found the boundary this document had stated -- "caught once the intermediate lives longer than one poll interval" -- was itself imprecise: an intermediate made to live nearly seven poll intervals *before* forking the survivor, then exiting immediately *after*, still missed the survivor 8 of 8 times, since what matters is not the intermediate's own total lifetime but whether it stays alive for at least one poll interval *after* the fork, long enough for a poll to observe the specific parent-child edge connecting it to the survivor. Made to linger after forking instead, it was caught 8 of 8 times. Both directions confirm the boundary is real. That condition is necessary but not sufficient: at some poll, an unbroken chain of such edges -- all present together in that one poll's own snapshot -- must connect the survivor back to a pid already a valid root going into that poll (the harness, or a pid a strictly earlier poll had already added), not merely one edge intact in isolation. A single poll's own traversal can catch several brand-new generations at once with no earlier poll ever having seen the intermediate links individually, and because every pid ever added remains a valid root for every later poll too, a long chain is also routinely completed incrementally across many different polls, long after an upstream ancestor has died. What permanently breaks discovery is a descendant for which no poll, ever, catches an intact chain back to whatever was a valid root at that moment. An eleventh post-closure round found and reproduced two counterexamples to an intermediate restatement of this same boundary that had required each link to be individually caught while its own parent was already tracked -- disproving it both by catching three brand-new generations at once in a single, first-ever poll, and by showing a link the tracker never re-validated as a root still had its downstream discovered once caught earlier. Corrected to the transitive, single-poll-or-incremental condition stated above. An eighth post-closure round separately reproduced a two-level case that genuinely defeats even that condition: an intermediate that forks-and-exits too fast for any poll to link it back to the harness leaves its own child (the real escapee) untracked from the start -- the very first link is the one that's missed -- even though that escapee goes on to live for over four seconds and later forks a survivor of its own with an edge that stays intact for 29 consecutive poll intervals; both were missed 8 of 8 times, because a child that was never added can never itself become a root, so nothing beneath it can ever be discovered no matter how long it persists. Closing this for real would need an OS-level process-lifecycle notification mechanism (e.g. `kqueue`'s `EVFILT_PROC`/`NOTE_TRACK`, or an eBPF/DTrace-based hook) rather than periodic polling -- out of scope for a Phase 0 spike proving mechanisms (post-closure fix, disclosed not fixed; this document's earlier "fixed" framing for the daemonize-escape item as a whole was corrected to reflect this).
- **Polling the process tree every `descendantPollInterval` has a real, measured cost that was previously asserted rather than shown.** A single `ps -axo pid=,ppid=,lstart=` snapshot over roughly a thousand processes took on the order of tens of milliseconds in testing; at the production 150ms interval that is a small but non-zero, continuous background cost for the harness's entire life, multiplied by however many attempts run concurrently in a fleet. Not a problem at the scale this spike tests, but Phase 1/2 should treat this as a real resource line item when sizing concurrent-attempt limits, not assume it away (post-closure fix, disclosed not fixed).

## Post-closure fix: daemonize escape and control-channel write serialization

Requested by the boss after the fable-model review landed, to actually close both surfaced gaps rather than leave them as accepted limitations. Both were fixed under the same ultrawork discipline as the four verification-gate rounds: strict RED-then-GREEN tests, plus live manual-QA evidence for the user-facing invariant.

1. **Control-channel write serialization, fixed.** `control.go`'s `ControlChannel.Send` now holds its mutex across the entire marshal-and-write, not just the `conn` field read, so the main goroutine (`runner_started`/`harness_exited`/`termination_complete`) and the `ReadLoop` goroutine (`pong`) can never interleave their writes mid-syscall. Proving this needed a deterministic test, not a real-socket stress test: a real Unix domain socket's `Write` turns out to already be atomic against concurrent writers at practical test sizes on this platform, even up to several MB (verified empirically -- both this project's own testing and a dedicated post-closure verification-gate round confirmed this independently), so `TestControlChannel_SendSerializesAcrossTheWholeWrite` instead uses a deliberately slow `net.Conn` stand-in (`slowConn`, splitting each write into two chunks with an artificial delay between them) to force a real interleaving window independent of platform write-atomicity quirks. RED (genuinely interleaved, invalid JSON) then GREEN. `TestControlChannel_ConcurrentSendsNeverInterleaveOnTheWire`'s own comment was corrected after a post-closure review round found it overstated what a real-socket test alone can prove.
2. **Daemonize escape, substantially narrowed via continuous tracking, not a point-in-time snapshot -- with one structural gap that remains open, disclosed below rather than papered over.** The first attempt at this fix (a single `descendantsOf` snapshot taken once, immediately before running the group and pid-list kills concurrently) was itself rejected by a dedicated post-closure verification-gate round: it missed the natural-harness-exit case entirely (the harness is already reaped, and any escaped descendant already reparented to init, by the time termination begins) and a mid-graceful-window escape (a descendant that appears after termination starts but before the group is confirmed gone), and it collapsed EPERM into "gone" for the pid-list path exactly like round 1's original group-side bug. All three were real, reproduced findings; see "Post-closure verification-gate round 1" below for the full account. The corrected design: `runner/cs-runner/descendant_tracker.go` (new) starts polling the OS process tree (via `processtree.go`'s `descendantsOfAny`, seeded with the harness pid plus every pid already tracked) once the harness is spawned and its reaper and manifest write are already in place, and keeps polling continuously -- through the harness's entire normal life, and through the full graceful-wait/hard-kill/verify sequence -- accumulating every descendant pid still confirmed alive (one that fails revalidation, having exited or been recycled by the OS, is pruned rather than kept forever), so a descendant is caught as long as, at some poll, an unbroken chain of parent-child links -- all present together in that one poll's own snapshot -- connects it back to a pid already a valid root going into that poll: the harness itself, or a pid a strictly earlier poll already added. A single poll's own traversal walks that snapshot to any depth, so it can catch several brand-new generations at once with no earlier poll ever having seen the intermediate links individually (this is why even the tracker's first, synchronous poll can catch a multi-generation escape in one pass, not just a direct child). And because every pid ever added remains a valid root for every later poll too, a subtree already reached through some ancestor keeps being explored on future polls even after that ancestor has since died and been pruned -- a long chain is routinely completed incrementally this way, across many different polls, long after an upstream link has broken. What permanently breaks discovery is a descendant for which no poll, at any point in the harness's life, ever catches an intact chain back to whatever was a valid root at that moment: in practice, one specific link on the path back to the harness was already severed before any poll's snapshot could ever catch both ends of it together, so the child beyond that missed link can never itself become a root, and everything beneath it is invisible no matter how long it subsequently runs (see the double-fork Known Limitations bullet below, which is exactly this case). `termination.go`'s `TerminateGroupAndDescendants` runs the group-scoped `Terminate` first, then `terminateTrackedDescendants`, which keeps the tracker running and re-polls its live accumulated set (via `Peek()`, not a one-shot snapshot) for its own entire SIGTERM-wait-SIGKILL-verify sequence, so a descendant that appears during that sequence -- not just before it starts -- is still caught; both phases run independent of each other's outcome, using the same EPERM-safe tri-state liveness check (`checkPID`) as the group path, plus a fresh process-identity revalidation before signaling any newly-discovered pid. `main.go`'s `terminateAndFinalize` (the sole termination call site) threads the tracker through every code path that can end a runner's life. This continuous-tracking design's own first implementation was itself rejected by a second post-closure verification-gate round with five more real findings -- all in the tracking/termination mechanics, not the underlying design -- fully described in "Post-closure verification-gate round 2" below, which is also where the current, corrected behavior (unconditional dual-phase execution, poll-failure-as-unverified, pid-identity revalidation, a bounded `ps` call) is defined. Live evidence: `daemon/spike_scripts/spike_c_daemonize_escape_driver.exs` plus `daemon/priv/fake_harness_with_daemonizing_grandchild.sh` reproduce the exact live-tmux daemon-kill demonstration from earlier in this document, but with the harness spawning a real escaping grandchild; confirmed live, against the current code, that `kill -9` of the daemon left all four processes -- daemon, cs-runner, harness, *and the escaped grandchild* -- gone, with the manifest recording `dead_verified`/`control_eof`. A third post-closure round confirmed all findings from rounds 1 and 2 held, then found and closed two more real defects in the tracking mechanics themselves (see "Post-closure verification-gate round 3" below). A fourth post-closure round confirmed rounds 1-3's fixes all held, fixed one more real, cheaply-closable gap (a tracked descendant's own children forked *after* the harness itself had died and been reaped were never discovered, since polling was rooted only at the harness's pid), and found that this document's "fixed" framing for the daemonize-escape item as a whole had been overstated: the classic double-fork daemonize idiom (an intermediate process that calls `setsid()` then exits within roughly a millisecond, before forking the process that actually survives) severs the process-tree link back to the harness far faster than any poll interval can practically observe, and remains genuinely unclosed -- see "Post-closure verification-gate round 4" below for the full account, including why this is a structural limit of process-tree polling rather than a bug with a further fix. A fifth post-closure round found round 4's own two fixes were each incomplete in a way that reopened the exact bug class they had just closed (see "Post-closure verification-gate round 5" below); a sixth confirmed those fixes held, then found the tracker was left running (leaking its background goroutine) on an error return path introduced by round 5's own rewrite, plus stale contract comments and a stale description in this very paragraph (see "Post-closure verification-gate round 6" below); a seventh confirmed round 6's code fix held, then found the double-fork boundary condition itself had been stated imprecisely in three places (see "Post-closure verification-gate round 7" below); an eighth confirmed all code from rounds 1-7 holds under a fresh, from-scratch adversarial pass, then found round 7's own corrected wording was itself still imprecise (in the direction that overclaims safety, not undersells it) plus two stale round-count/pointer slips and an undisclosed 2x termination-time consequence of running the group and descendant kill phases sequentially -- all corrected (see "Post-closure verification-gate round 8" below); round 10 confirmed the code holds a fourth consecutive time, found the same round-count arithmetic slip recurring a third time, and found round 9's own corrective wording had itself overcorrected -- stating the mechanism requires the whole chain intact in a single snapshot, when the relay case round 9 had just confirmed proves discovery is normally incremental across many different polls -- corrected to state the real mechanism: each link is caught independently, and only a single never-caught link permanently breaks discovery beneath it (see "Post-closure verification-gate round 10" below); round 11 found round 10's own restatement was itself still wrong -- it required each link to be individually caught while its own parent was already, separately, a tracked root, when in fact a single poll's own traversal can catch several brand-new generations at once (reproduced: three generations discovered in one single, first-ever poll) -- corrected to the combined condition stated in the paragraph above (see "Post-closure verification-gate round 11" below). ### Post-closure verification-gate round 1: rejection, and what it caught

The first attempt at the daemonize-escape fix (described above as superseded) was submitted to the same `omo:reviewer` verification-gate process used for the original four rounds. It was rejected with five findings, all reproduced live against the actual code, not hypothetical:

- **A failed process-tree snapshot silently skipped the group kill entirely.** The original design took one `descendantsOf` snapshot up front and returned immediately on error, before ever calling `Terminate`. With `ps` unreachable (a broken `PATH`), the harness's own process group -- the one part of termination that has nothing to do with process-tree visibility -- was never signaled at all. **Fixed** by the tracker design: `TerminateGroupAndDescendants` no longer takes any snapshot itself: it calls the group-scoped `Terminate` unconditionally first, and a failed or empty tracker simply contributes zero pids to the (harmless, no-op) pid-list phase afterward.
- **The escape was not closed on the natural-harness-exit path.** The harness is reaped (via `Cmd.Wait()`) before `terminateAndFinalize` is ever called on that path, so a single snapshot taken inside `TerminateGroupAndDescendants` always ran too late -- the escaped descendant had already been reparented to init, severing the very link the snapshot needed. **Fixed** by tracking continuously from the moment the harness is spawned, independent of when (or whether) termination is ever triggered.
- **A descendant that escaped mid-graceful-window was missed.** The original design took its one snapshot *before* running the group kill, so anything that appeared during the 5-second graceful-wait/hard-kill window was invisible to it. **Fixed** by keeping the tracker running through that entire window and only reading its accumulated results afterward.
- **EPERM (unverifiable) was misread as "gone" for the pid-list path** -- exactly round 1's original finding B2, reintroduced in the new pid-list code (`sendSignal(pid, 0) == nil` treated any non-nil result, including EPERM, as "not alive, skip"). **Fixed**: `checkPID` mirrors the group path's three-state `groupGone`/`groupAlive`/`groupUnknown` check, and `waitUntilPIDsGone` only resolves on a conclusive `groupGone`.
- **Documentation and code comments overclaimed or were stale**: the criterion-4-style claim that a snapshot taken "after the group-scoped termination has already had its full timeout budget" was factually backwards (it was taken *before*), and a test comment asserted a 500KB real-socket payload made write interleaving "virtually certain" when direct measurement (both in this project and independently by the reviewer) showed the opposite. **Fixed**: both corrected in place.

All five were fixed with new RED-then-GREEN tests (the fixes and tests are described in the numbered list above, since the corrected design superseded the original). A genuine implementation bug was also found and fixed while building the fix for finding 2: the tracker's very first poll could, in principle, be delayed by goroutine scheduling past the point a fast-exiting root process had already vanished, defeating even the continuous-tracking design for an adversarially instant test case; making that first poll run synchronously before `startDescendantTracker` returns closed it. Full regression after this round's fixes: Go suite grew to 37 real tests (38 `func Test*` matches including `TestMain`, the re-exec helper hook, which is not itself a test case) -- clean under `gofmt -l`/`go vet ./...`/`go test ./... -race -count=2`; Elixir `daemon/` suite 43 tests (1 doctest, 42 tests) clean; the escape-scenario tests repeated 8-10x under `-race` with zero flakes; the mid-graceful-window test (which takes ~5s per run, matching its own timeout budget) repeated 3x clean; no leftover `/tmp/csc-*` directories or stray processes after any run.

### Post-closure verification-gate round 2: rejection, five more findings in the tracking mechanism itself

The continuous-tracking design's first implementation was submitted to a second post-closure verification-gate round. The reviewer independently re-verified all five round-1 findings held (they did) and reproduced two live scenarios (the base daemon-kill demonstration and the daemonize-escape one), then found five more real, reproduced defects -- all in how the tracking and termination mechanics were wired together, not in the underlying continuous-tracking design itself:

- **A hung or slow `ps` could abandon an already-spawned harness.** `startDescendantTracker`'s synchronous first poll was called between `SpawnHarness` and both the harness-reaping goroutine and the "running" manifest write (which persists `harness_pid`/`pgid`) -- so a `ps` that hung left a live harness with no reaper watching it and no on-disk record of its pid at all. Reproduced with a stub `ps` that blocks: `run()` stayed blocked with the manifest stuck at `starting` and no pgid recorded, for as long as the harness was alive. **Fixed** by reordering `main.go`: the reaper goroutine and the "running" manifest write both now happen before the tracker is started at all (with a fallback that starts the tracker immediately, right before best-effort cleanup, if the manifest write itself fails after the harness is already spawned).
- **The same unbounded `ps` call could hang `Stop()` -- and therefore the entire termination path -- forever.** `descendantTracker.Stop()` waits on the tracker's background goroutine finishing a final poll; with no timeout on the underlying `ps` invocation, that poll (and therefore `Stop()`, and therefore `TerminateGroupAndDescendants`, and therefore `run()`) could block indefinitely. Reproduced: `go test -test.timeout 20s` against a hung stub `ps` panicked with the goroutine parked inside the `ps` call. **Fixed** by bounding every `ps` invocation in `processtree.go` with `exec.CommandContext` and a `psSnapshotTimeout` (2 seconds).
- **A failed descendant enumeration was silently treated as "saw nothing," which `TerminateGroupAndDescendants` could then report as fully verified even with a real escapee still alive.** The tracker discarded a poll's error entirely, and an empty pid list vacuously verified as `true`. Reproduced with `ps` unavailable and a real `setsid()` grandchild alive: `TerminateGroupAndDescendants` returned `verified=true` while the escapee was still running -- the exact "unverifiable treated as gone" class this codebase had already fixed twice elsewhere (round 1 finding B2, and round 1 of this post-closure gate's own finding). **Fixed**: the tracker now records whether any poll ever failed and `Stop()` returns that as a `reliable` flag alongside the pids; `TerminateGroupAndDescendants`'s overall `verified` result is `false` whenever tracking was ever unreliable, never just whatever the (possibly incomplete) pid list happened to verify.
- **A failed group-scoped signal skipped the descendant phase entirely -- the mirror image of round-1 finding B1, in the other direction.** `TerminateGroupAndDescendants` returned early on a group-phase error before ever calling `terminatePIDList`, so a trackable, individually-killable escaped descendant went completely untouched whenever the unrelated group-scoped signal failed (e.g. EPERM on the negative-pgid broadcast, a case `docs/protocols/runner.md` explicitly anticipates). Reproduced by stubbing `sendSignal` to EPERM only negative (group) pids while allowing positive (individual) pids through: the descendant was never signaled. **Fixed**: the descendant phase now always runs, independent of the group phase's outcome; the two errors (if any) are combined via `errors.Join`.
- **Every tracked pid was signaled unconditionally, with no check that it was still the same process** -- the pid-reuse risk this document had already disclosed (as low-probability) was, in practice, closer to real than assumed: on the reviewer's machine, plain pid churn was fast enough (~7 pids/sec system-wide) that a long-running harness's tracked pid list could plausibly go stale within its lifetime, and blindly SIGKILLing a stale pid means signaling whatever unrelated process the OS has since assigned that number to. **Fixed**: `processtree.go` now captures each process's start time (`ps`'s own `lstart` rendering) alongside its pid, and `terminatePIDList` revalidates every tracked pid against a fresh snapshot immediately before signaling anything -- a pid whose current start time no longer matches what was recorded (already exited, or recycled to a different process) is treated as already resolved and is never signaled or waited on. If the revalidation snapshot itself fails, nothing is signaled and the whole call reports unverified rather than guessing.

Four smaller, non-blocking items were folded in alongside the five above: `descendantTracker.Stop()` is now idempotent (`sync.Once` around closing its stop channel) rather than panicking if ever called twice, even though nothing in this codebase currently does so; the `descendantPollInterval` comment's unmeasured "not a meaningful resource burden" claim was replaced with an honest, measurement-backed disclosure (see Known Limitations below); the sub-poll-interval miss's effect on the manifest is now stated explicitly rather than implied (also below); and a stale comment cross-reference in `control_test.go` ("the slowConn test below," when that test is above) was corrected.

New RED-then-GREEN tests: `TestPSSnapshot_TimesOutRatherThanHangingForever`, `TestDescendantTracker_ReportsUnreliableAfterAFailedPoll`, `TestDescendantTracker_StopIsSafeToCallTwice`, `TestTerminateGroupAndDescendants_DescendantPhaseStillRunsWhenGroupPhaseErrors`, `TestTerminatePIDList_NeverSignalsAPidTheOSHasRecycledToAnUnrelatedProcess`, and `TestTerminatePIDList_UnableToRevalidateReportsUnverifiedWithoutSignalingAnything`; the pre-existing `TestTerminateGroupAndDescendants_GroupStillTerminatesWhenDescendantTrackingCanNeverSeeAnything` was renamed and its assertion corrected (it previously asserted the very `verified=true` behavior this round found to be a bug). Full regression after this round's fixes: Go suite is now 43 real tests (44 `func Test*` matches including `TestMain`) -- clean under `gofmt -l`/`go vet ./...`/`go test ./... -race -count=1` and `-race -count=3 -shuffle=on`; Elixir `daemon/` suite 43 tests (1 doctest, 42 tests) clean; both live-tmux scenarios (the base daemon-kill demonstration and the daemonize-escape one) reproduced again against the corrected code with the same outcome as before; no leftover `/tmp/csc-*` directories or stray processes (including any `CS_RUNNER_TEST_HELPER=daemonize` re-exec helper) after any run.

### Post-closure verification-gate round 3: rejection, two blocking findings and one genuinely unclosable claim narrowed

A third post-closure verification-gate round independently re-verified every finding from both prior rounds (all held) and both live-tmux scenarios (both reproduced cleanly), then found two blocking defects and confirmed the polling-cost disclosure was accurate:

- **`psSnapshotTimeout` did not actually bound `psSnapshot` against every kind of hang.** `exec.CommandContext`'s cancellation only kills the direct `ps` process; if `ps` forks a child before dying (or is itself a wrapper script that does) and that child inherits the stdout pipe's write end, `Output()` keeps blocking on a read that will never see EOF until the orphan exits on its own, regardless of the context's own timeout having already fired. Reproduced as a genuine 61-second hang of the real runner against a `ps` shim built exactly this way, and confirmed this reopens both N1's and N2's original symptoms (an already-spawned harness left without a persisted pgid until the orphan exits; the termination path hung past any reasonable bound) just past the point the context timeout appears to close them. **Fixed** by setting `cmd.WaitDelay` (`psWaitDelay`, 1 second) on the `ps` command: once the context's own timeout has already tried to kill the process, `WaitDelay` forces the pipe closed after this additional grace period regardless of what still holds it open, rather than waiting on it indefinitely.
- **The N1 ordering fix (reaper and manifest write ahead of descendant tracking) had no regression test.** Proven by mutation: reverting `main.go`'s ordering back to starting the tracker immediately after spawn (the exact shape round 2 rejected) still passed the full test suite, meaning nothing would have caught this regression if it were ever reintroduced. **Fixed** with a new test, `TestRun_RunningManifestAndReaperAreNotDelayedByDescendantTrackingsFirstPoll`, which puts a slow `ps` on `PATH` and asserts the "running" manifest (with a populated `harness_pid`/`pgid`) appears well within a bound far shorter than the slow `ps`'s own delay; confirmed genuinely RED against the reverted ordering (manifest stuck at `starting`) and GREEN against the current code.

Seven documentation-only findings were also folded in: the `processtree.go` "What was built" line and the discarded-error Known Limitations bullet were updated to mention the `lstart` capture and the widened `errors.Join` respectively; the test-seam count was corrected from three to four (`currentStartedAtFn` was missing); the sub-poll-interval residual-window bullet now notes that `main.go`'s pre-tracking `sha256File` hash (moved there by the N1 fix) is itself a second, size-dependent term in that window, not just the poll interval; and the pid-reuse mitigation bullet now discloses two narrower gaps a third round found in the mitigation itself -- `lstart`'s one-second granularity (a same-second pid recycle passes revalidation undetected) and the fact that only descendant pids are revalidated, never the tracker's own root (harness) pid, which is polled again and again for the tracker's entire life with no equivalent check it still refers to the same process.

Full regression after this round's fixes: Go suite is now 45 real tests (46 `func Test*` matches including `TestMain`) -- clean under `gofmt -l`/`go vet ./...`/`go test ./... -race -count=1` and `-race -count=3 -shuffle=on`; the new ordering-regression test repeated 8x clean; Elixir `daemon/` suite 43 tests (1 doctest, 42 tests) clean; both live-tmux scenarios reproduced again against the corrected code with the same outcome as before.

### Post-closure verification-gate round 4: one real gap closed, one structural limitation found and disclosed, one doc correction only half-applied

A fourth post-closure verification-gate round confirmed both of round 3's findings held and every finding from rounds 1-2 still held, then found three more items -- two blocking, one documentation-only:

- **A tracked descendant's own children, forked after the harness itself had died and been reaped, were never discovered.** `descendantTracker.poll` always enumerated descendants of the harness pid alone. Once the harness was gone, that enumeration returned nothing forever, so anything a still-alive tracked escapee forked afterward -- even minutes later, even though every process involved lived for many poll intervals -- was invisible. Reproduced end to end through `run()`: a harness backgrounds a `setsid()` escapee that ignores SIGTERM, the harness exits naturally, and the escapee forks a new child during the termination sequence's own graceful-wait window; the manifest recorded `dead_verified` while that grandchild was still alive. **Fixed**: every pid the tracker has ever seen now acts as its own polling root, not just the harness -- `descendantsOf` was generalized into `descendantsOfAny(roots []int)`, and each poll passes the harness pid plus everything accumulated so far. A tracked descendant's own later children are now discovered the same way the harness's own children always were.
- **The double-fork daemonize idiom is not, and cannot practically be, closed by process-tree polling -- this document's "fixed" framing for the daemonize-escape item was overstated.** The fix closes any escape whose parent-chain link back to the harness survives at least one poll interval (150ms in production) -- a harness that directly backgrounds a `setsid()` process, for instance. The classic daemonize idiom is different: an *intermediate* process forks, calls `setsid()`, forks the process that actually survives, and exits immediately -- typically within a millisecond or so, since it does nothing else. If that intermediate dies before any poll ever observes it, its child was never a discoverable descendant of the harness in the first place: by the next poll, the child has already been reparented to init, with no process-tree link connecting it back to the harness at all. This is not a sub-poll-interval *timing* race that a faster interval narrows -- shrinking `descendantPollInterval` cannot help, since spawning `ps` itself costs tens of milliseconds and an intermediate's real lifetime is on the order of a millisecond; no realistic polling frequency can reliably observe it. Reproduced end to end through `run()`'s real control-channel-EOF path with the real binary: 14 of 18 iterations left the double-fork daemon alive with the manifest reporting `dead_verified`. The boundary is not the intermediate's own lifetime but whether it stays alive for at least one poll interval *after* forking the survivor, long enough for a poll to observe that specific parent-child edge -- a seventh post-closure round confirmed this by making the intermediate live nearly seven poll intervals *before* forking and exit immediately *after*, which still missed the survivor 8 of 8 times, versus lingering *after* the fork instead, which caught it 8 of 8 times. This is necessary but not sufficient: at some poll, an unbroken chain of such edges -- all present together in that one poll's own snapshot -- must connect the survivor back to a pid already a valid root going into that poll (the harness, or a pid a strictly earlier poll had already added). A single poll's own traversal can catch several brand-new generations at once with no earlier poll ever having seen the intermediate links individually, and because every pid ever added remains a valid root for every later poll too, a long chain is also routinely completed incrementally across many different polls, long after an upstream ancestor has died. What permanently breaks discovery is a descendant for which no poll, ever, catches an intact chain back to whatever was a valid root at that moment (an eleventh post-closure round found and corrected an intermediate restatement of this boundary that had wrongly required each link to be individually caught while its own parent was separately tracked, disproving it by catching three brand-new generations in a single first poll). An eighth post-closure round separately reproduced a two-level counterexample that genuinely defeats even the corrected condition: a harness backgrounds an intermediate that itself forks-and-exits too fast for any poll to link it back to the harness, so that intermediate's own child (the actual escapee) is never tracked at all -- the very first link is the one missed -- even though that escapee then lives for over four seconds and, well after it is already alive and being polled, forks a survivor of its own with an edge that stays intact for 29 consecutive poll intervals. Both were missed 8 of 8 times, because a child that was never added can never itself become a root, so nothing beneath it can ever be discovered. **Not fixed, and not closable within this design** -- closing it for real would need an OS-level process-lifecycle notification mechanism (e.g. `kqueue`'s `EVFILT_PROC`/`NOTE_TRACK`, or an eBPF/DTrace-based hook) rather than periodic `ps` polling, which is out of scope for a Phase 0 spike proving mechanisms. Disclosed in Known Limitations below rather than left implied-fixed by this section's earlier framing (now corrected).
- **A prior documentation correction was only half-applied (documentation-only).** Round 3's own record claimed the test-seam count had been corrected from three to four; it had been corrected in the round-2 narrative paragraph but not in the Known Limitations bullet that actually carries the limitation forward. Corrected above.

New RED-then-GREEN test: `TestDescendantTracker_TracksAChildForkedByAnAlreadyTrackedDescendantAfterRootExits`, confirmed genuinely RED (via mutation, reverting the poll to the harness-pid-only root) then GREEN. The double-fork gap is disclosed, not test-covered with a passing assertion, since there is nothing this design can assert beyond "this fails" -- a Known Limitations bullet with the reproduction details above serves that purpose instead, matching how every other genuinely unclosable limitation in this document is handled.

Full regression after this round's fixes: Go suite is now 46 real tests (47 `func Test*` matches including `TestMain`) -- clean under `gofmt -l`/`go vet ./...`/`go test ./... -race -count=1` and `-race -count=3 -shuffle=on`; Elixir `daemon/` suite 43 tests (1 doctest, 42 tests) clean; both live-tmux scenarios reproduced again with the same outcome as before (both exercise the single-hop escape shape that is actually closed, not the double-fork shape that is not -- consistent with the narrowed claim above).

### Post-closure verification-gate round 5: two real gaps found in what round 4 called fixed

A fifth post-closure verification-gate round confirmed rounds 1-4's fixes all held (including reproducing round 4's own unit test by mutation), confirmed the double-fork disclosure's reproduction numbers were directionally accurate (13/18 and 0/4 against a fresh reproduction, close enough to round 4's 14/18 and 4/4 to confirm the same real boundary, not a fabricated one), then found two more real, blocking defects -- both, in effect, incomplete applications of round 4's own fix:

- **A descendant forked during the descendant-kill phase's own graceful-wait/verify window was still untracked and unsignaled.** `TerminateGroupAndDescendants` called `tracker.Stop()` -- halting all polling -- *before* running the descendant-kill sequence, so that sequence's own multi-second SIGTERM-wait-SIGKILL-verify budget (up to `gracefulTimeout` + `verifyTimeout`, 7 seconds in production) ran with zero process-tree observation. Reproduced end to end through `run()`, verbatim against round 4's own stated reproduction wording: a harness backgrounds a `setsid()`-escaping, SIGTERM-ignoring descendant and exits naturally; the descendant forks a brand-new child 1.5 seconds later, squarely inside the descendant phase's own graceful window; the manifest recorded `dead_verified` while that new child was still alive. **Fixed**: the descendant-kill sequence (renamed `terminateTrackedDescendants`) now keeps the tracker running for its entire duration, calling `tracker.Peek()` (a new method that reads the tracker's live accumulated set without halting it) throughout both the SIGTERM and SIGKILL phases, and only calls `Stop()` once, right before returning. The tracker's own background polling -- which already treats every previously-seen pid as an extra root (round 4's fix) -- keeps discovering new forks throughout, not just before this function was ever called.
- **Round 4's fix made every previously-seen pid a permanent, never-revalidated polling root**, which reopened exactly the class of bug pid-identity revalidation was built to close, one step earlier in the pipeline: a pid that exited and was recycled by the OS to an unrelated process would keep acting as a polling root forever, sweeping that unrelated process's real children into the tracked set -- children recorded with their own correct, matching start times, so the later identity-revalidation step (which only checks "is this the process I recorded?") could not catch them at all. Reproduced against the real termination path: an unrelated process's real child was signaled and killed. **Fixed**: `descendantsOfAny` now revalidates every root that carries a recorded identity (i.e. every previously-seen pid, as opposed to the harness's own top-level root, whose identity this package still does not track) against the very same snapshot it uses for traversal, before ever traversing from it; a root that no longer matches is excluded from traversal, and the tracker prunes it from its own accumulated set so it stops being used as a root on every subsequent poll too.

### Post-closure verification-gate round 7: the double-fork boundary was stated imprecisely, in the wrong direction to be safe

A seventh post-closure verification-gate round independently reproduced round 6's `defer` fix by mutation (confirmed genuinely RED and GREEN), ran independent goroutine-accounting across 60 calls (no leak), reproduced both live-tmux scenarios, and found the entire code fix from rounds 1-6 holds. It then did a fresh, from-scratch reproduction of the double-fork boundary rather than trusting the numbers this document already carried, and found three current-state claims -- all rewritten by round 6 or earlier and asserted as accurate -- described the wrong condition:

This document and `descendant_tracker.go`'s own comment had stated the boundary as "the intermediate's own lifetime relative to one poll interval": live past one poll interval, get caught; die within one, get missed. The round built an intermediate that lives nearly seven poll intervals *before* forking the process that actually survives, then exits immediately *after* forking it -- and the survivor was still missed 8 of 8 times. Made to linger *after* the fork instead, it was caught 8 of 8 times. The real condition is not how long the intermediate lives in total, but whether it stays alive for at least one poll interval *after* forking its child -- long enough for a single poll to observe that specific, and only that, parent-child edge. An intermediate that lives a long time and then exits right after forking is just as invisible as one that never lived at all; conversely, a very short-lived intermediate that happens to linger past the fork is caught.

This mattered in the safe direction to fix, not the safe direction to have shipped: the prior wording ("caught once the intermediate lives longer than one poll interval") could be read as implying more of the double-fork idiom's real-world shapes are covered than actually are, in a mechanism that writes `dead_verified`. No code change was needed or made -- this is the same disclosed, structural polling limit as before, correctly restated. Corrected in three places: this section's own paragraph above, the `descendant_tracker.go` struct comment, and both the round-4 narrative and Known Limitations statements of the double-fork boundary.

### Post-closure verification-gate round 11: round 10's restatement required each link to be individually tracked, but a single poll can catch multiple new generations at once

An eleventh post-closure verification-gate round confirmed the code has needed no changes since round 6 for a fifth consecutive round (independently, via its own mutation test of `poll()`'s prune-then-add ordering and its own live reproduction of both scenarios), then found round 10's own restatement of the boundary was itself wrong, in the under-claiming direction:

Round 10's wording required every link in a chain to be "caught by SOME poll while its parent side is already a valid root (the harness pid, or a pid an earlier poll already added)" -- meaning an intermediate had to have already been separately tracked before the link beneath it could be caught. This is not how `descendantsOfAny`'s BFS actually works: at a single poll, the traversal walks that poll's own snapshot to any depth from a valid root, discovering as many new, never-before-seen generations as are connected in that one snapshot, all at once -- none of the intermediates need to have been tracked by an earlier poll. Reproduced directly: a chain harness→A→B→C, fully intact before tracking ever starts, run through only the tracker's synchronous first poll (no second poll had a chance to run) -- A, B, and C were all discovered together. Under round 10's wording, neither A→B nor B→C should have been catchable, since at that first poll neither A nor B had been "added by an earlier poll." A second reproduction showed the mirror case: A killed immediately after the first poll (so at no point was A "still a valid root" on any poll where B needed catching after A's death), yet B and C -- caught earlier while the chain was intact -- persisted correctly. This also directly contradicted this document's own round-9 record (the "Post-closure fix" paragraph's earlier text, and the still-present note in round 9's own section) that several brand-new links can be caught together within a single poll, and it would have made the tracker's synchronous-first-poll design (built specifically so a harness that "spawns an escaping grandchild and exits almost immediately" is still caught) pointless for exactly that case.

**Fixed** by combining both real mechanisms into one correct statement, in all five affected places (`descendant_tracker.go`'s struct comment; the "Post-closure fix" paragraph; both Known Limitations statements of the double-fork boundary; and a corrective note added to round 10's own section rather than silently rewriting history): a descendant is discovered if, at some poll, an unbroken chain of parent-child links -- all present together in that one poll's own snapshot -- connects it back to a pid that was already a valid root going into that poll (the harness, or a pid a strictly earlier poll had already added). A single poll's traversal can close out several brand-new generations at once (this is what the synchronous first poll is for), and separately, because every added pid remains a valid root for every later poll too, a chain can also be completed incrementally across many different polls after an earlier link died. What permanently breaks discovery is a descendant for which no poll, ever, catches an intact chain back to whatever was a valid root at that moment.

No code was changed in this round; this was a documentation correction, verified this time by directly reproducing the exact case the corrected wording claims works (single-poll multi-generation discovery) rather than only re-testing previously-covered scenarios.

Full regression after this round (no code changed, comments and documentation only): Go suite remains 49 real tests, `gofmt -l`/`go vet ./...`/`go test ./... -race -count=1`/`-race -count=3 -shuffle=on` all clean; Elixir suite unchanged at 43 tests; both live-tmux scenarios reproduced again with the same outcome as before.
