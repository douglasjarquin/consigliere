# Harness adapter protocol

This document specifies the contract between consigliere-next's daemon and a coding harness (Claude Code, Codex, or another CLI-driven agent), added in Phase 3 once the runner protocol (`docs/protocols/runner.md`) and daemon kernel exist.
V1 supports exactly one harness, per master-prompt section 4.10; this contract exists so that harness is pluggable in principle, not so a second harness is built early.

## Why a normalized contract, not per-harness special casing

Firstmate's `docs/` directory carries five separate terminal-backend docs (tmux, herdr, zellij, orca, cmux) and five separate per-harness `supervision-protocols/*.md` files (claude, codex, grok, opencode, pi), each with its own liveness-classification logic duplicated in `fm-composer-lib.sh` and `fm-busy-lib.sh`.
That is N backends times N harnesses worth of special-cased "is this thing alive and what is it doing" logic, grown incrementally over hundreds of commits, a large fraction of which were bug fixes for exactly this liveness-classification problem.
The adapter contract below exists specifically to prevent that shape from recurring: every harness integration implements the same seven functions and emits the same event vocabulary, and the daemon never contains a single `if harness == "codex"` branch outside the adapter boundary.

Symphony's Codex integration (`Codex.AppServer`, a JSON-RPC-over-stdio Erlang Port) is a reasonable low-level transport pattern to borrow (structured framing over a subprocess's stdio), but its session identity (`thread_id`) lives only inside the owning Task's process dictionary with no external manifest; a crash of that Task loses the ability to resume the session at all. The adapter contract below requires `native_session_id` to be reported to the daemon and persisted on the Attempt row specifically so this failure mode cannot recur; session identity is daemon state, not adapter-process state.

## Adapter interface

An adapter is a small piece of code, invoked by the daemon (via the runner, since the adapter's `start`/`resume`/`send`/`interrupt`/`cancel` calls ultimately translate into a runner-launched subprocess and control-channel traffic), implementing:

```text
capabilities() -> Capabilities
start(attempt_spec) -> SessionRef
resume(native_session_id, resume_metadata, context_pack) -> SessionRef
send(session_ref, input) -> ok | error
interrupt(session_ref) -> ok | error
cancel(session_ref) -> ok | error
snapshot(session_ref) -> Snapshot
```

`capabilities()` is a static, non-side-effecting call the daemon uses at startup and before scheduling to know what an adapter can do, e.g.:

```json
{
  "supports_native_resume": true,
  "supports_interrupt": true,
  "max_context_tokens": 200000,
  "harness_name": "claude-code",
  "harness_version": "2.x",
  "adapter_contract_version": 1
}
```

`start(attempt_spec)` launches a brand-new session (fresh-session continuation, the mandatory path per master-prompt section 8). `resume(...)` attempts native session resume (the optional path); an adapter that returns `supports_native_resume: false` from `capabilities()` never receives a `resume` call, and the daemon always falls back to `start` with a freshly composed context pack.

`SessionRef` is an opaque handle the daemon uses for subsequent calls; it is not required to be meaningful outside the adapter, but the daemon persists whatever `native_session_id` the adapter reports via the `session.started` event (below) on the Attempt row, so that a *future* daemon process (after a restart) can attempt `resume` without needing the same adapter-process instance to still exist.

## Normalized event vocabulary

Every event the adapter (via the runner) reports to the daemon is one of:

```text
session.started
turn.started
progress.reported
artifact.created
question.requested
approval.requested
checkpoint.created
usage.updated
turn.completed
session.completed
session.failed
```

Every event carries the same envelope:

```json
{
  "event_id": "01J...",
  "native_sequence": 17,
  "project_id": "01J...",
  "mission_id": "01J...",
  "attempt_id": "01J...",
  "session_id": "01J...",
  "timestamp": "2026-08-18T21:07:33.500Z",
  "payload": { }
}
```

`event_id` is generated by the adapter and must be stable across a retransmit (the same underlying harness event reported twice, e.g. after a runner reconnect, must carry the same `event_id` so the daemon can deduplicate); `native_sequence` is the adapter's own monotonic counter and is used, in combination with the Attempt's currently active fencing token, to reject a "stale native event sequence" arriving from a superseded Attempt (master-prompt Phase 3 required test).

`payload` shape is event-specific, for example:

```json
// question.requested
{"subject_type": "attempt", "subject_id": "01J...", "question": "...", "options": ["a", "b"], "recommendation": "a"}

// checkpoint.created
{"commit_sha": "9f2b1a...", "branch": "mission/01J.../work", "message": "..."}

// artifact.created
{"kind": "diff_summary", "path_or_url": "...", "content_hash": "sha256:..."}
```

`question.requested` and `approval.requested` are the adapter-level signals that ultimately produce a durable Question row (`docs/state-machines/question.md`); the adapter itself has no authority and does not block waiting for an answer, it only reports the request and the daemon takes it from there.

## What the adapter must never do

- Decide whether a checkpoint is "good enough" to import; it only reports the SHA the harness committed. Import/ancestry verification is the daemon's job (`docs/architecture/workspaces-and-git.md`).
- Answer its own `question.requested` event or otherwise exercise boss or advisory authority (`docs/architecture/authority-model.md`); it is not a principal in the authority model at all, it is a transport.
- Retain the only copy of `native_session_id`; that value must reach the daemon and be persisted before the adapter process can be considered to have done its job for that turn.
- Assume output silence means the session is dead. Silence is evidence for the daemon's Attempt-loss classification (which additionally requires process-inventory evidence, per invariant #11/#12), not a conclusion the adapter is entitled to draw and report as `session.failed`.

## Harness conformance suite

Before any harness adapter is trusted (used against a real Mission, not a fake/test harness), it must pass this black-box behavioral suite. Each item is phrased as an observable outcome, not an implementation detail, so the suite applies unchanged to a second harness added post-cutover.

1. **Cold start.** `start(attempt_spec)` with a minimal context pack produces exactly one `session.started` event before any `turn.started` event, and the reported `native_session_id` is non-empty.
2. **Ordinary completion.** A trivial task run to completion produces a `turn.started`/`turn.completed` pair and exactly one terminal event (`session.completed`), never both `session.completed` and `session.failed`.
3. **Progress visibility.** At least one `progress.reported` event is observable during a multi-step task, so `cs attempt logs` has something to tail before completion.
4. **Checkpoint reporting.** After the harness makes a commit, exactly one `checkpoint.created` event is emitted per commit, carrying the actual resulting SHA (verified against `git rev-parse HEAD` in the workspace at that moment), not a SHA the adapter guessed before the commit landed.
5. **Question round-trip shape.** When the harness asks a clarifying question (whatever its native mechanism is: a tool call, a specific stdout marker, a structured stop reason), the adapter converts it to exactly one `question.requested` event containing the actual question text, not a placeholder.
6. **Interrupt.** `interrupt(session_ref)` on a running session causes the harness to stop its current turn without the process exiting, and a subsequent `send` can still reach it (interrupt is not cancellation).
7. **Cancel.** `cancel(session_ref)` causes the underlying process group to terminate via the runner's termination sequence (`docs/protocols/runner.md`), verified dead, within that document's bounded timeouts.
8. **Native resume, success path.** For an adapter with `supports_native_resume: true`, calling `resume` with a `native_session_id` from a previous cleanly-ended session continues in a way the harness's own transcript/log shows as one logical conversation, not a fresh one.
9. **Native resume, failure path.** Calling `resume` with a `native_session_id` the harness no longer recognizes (simulate by using a made-up id) returns an error the daemon can distinguish from success, so the daemon's exactly-one-fresh-session-fallback logic (master-prompt Phase 3 required test) has something concrete to trigger on.
10. **Malformed/truncated event.** If the adapter is fed a native event stream artificially truncated mid-object (simulating a killed process), it does not silently drop the partial event into a "successful" parse; it must be classifiable as truncated/malformed by the daemon consuming it, not as a valid low-information event.
11. **Duplicate completion.** If the underlying transport (not the adapter's own bug) delivers the same terminal native event twice (e.g. a runner reconnect replaying a buffer), the adapter's `event_id` for both deliveries is identical, so daemon-side deduplication (required regardless of adapter behavior) has a stable key to work with.
12. **Context pack fidelity.** The exact content handed to `start`/`resume` is hashable and the adapter does not silently truncate, reorder, or append to it; the daemon's `input_context_hash` on the Attempt row must reflect what the harness actually received.
13. **No unsolicited privilege.** The adapter process, exercised through this suite inside the isolation boundary defined in `docs/architecture/authority-model.md`, cannot reach the daemon's SQLite file, the boss channel, or another Mission's workspace; this is asserted mechanically (attempted access fails at the OS/sandbox boundary), not asserted by the adapter's own good behavior.

An adapter that fails any item above is not scheduled against a real Mission; a failing item is a blocking bug in the adapter, not an acceptable known limitation.
