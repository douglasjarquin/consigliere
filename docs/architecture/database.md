# Database

Consigliere-next uses SQLite, in WAL mode, as the sole durable store for operational state.
This document formalizes the operational rules governing that store and summarizes the projections (tables) it holds and how they relate to one another.
It does not repeat every field of every table; the full field lists live in the domain-model section of the master architecture. This document focuses on relationships, the write path, the read path, and why the operational rules exist.

## Why SQLite, and why these rules

The single most direct piece of negative evidence from Phase 0 grounding is Made's `RunManager` (`internal/daemon/runmanager.go:44-77`), which is a plain `map[string]*run` behind a `sync.Mutex`, with no disk writes, no SQLite, no bbolt, and no spool of any kind (confirmed by grep across Made's `internal/` tree finding zero matches for `sqlite`, `database/sql`, `bbolt`, or `spool`).
Made's `ReviewDecisions` map of pending human-review waiters is the same shape: pure in-memory, guarded by a mutex, gone the instant the daemon process exits.
The consequence, also confirmed during grounding, is that any Made daemon restart loses every run, every pending finding, and every parked review decision unconditionally, with no way to recover any of it.
A mutex-guarded in-memory map is not durability; it is concurrency safety for state that was never going to survive a process restart in the first place.
Consigliere-next's serialized SQLite writer keeps the same concurrency-safety property Made's mutex gives it (only one writer touches the data at a time) while adding the one thing that mutex never had: the data survives the process that wrote it.

## Operational rules

**One serialized write path.** Every mutation goes through `Consigliere.DatabaseWriter` (see `architecture/runtime.md`), so there is never a race between two independent writers even though SQLite itself would raise `SQLITE_BUSY` if two connections tried to write concurrently. This is enforced structurally, not by convention: no other module holds a write-capable connection.

**Short transactions.** Every transaction started by the DatabaseWriter does the minimum necessary reads and writes and commits immediately. A transaction never spans a network call, a Git operation, a filesystem operation outside the database file itself, or a call into a model. Two concrete places where this rule would be easy to violate if not stated explicitly:

- Checkpoint import (`architecture/workspaces-and-git.md`, steps 7-10): it would be tempting to wrap "verify commit identity, neutralize Git config, import into the trusted mirror, and record the checkpoint" as one transaction for atomicity's sake. This must not happen. The Git import (step 9) is an external process operation with its own unpredictable duration and failure modes; running it inside an open SQLite transaction would hold a write lock for however long that external operation takes, blocking every other write in the system, and would also make the transaction's success or failure depend on an operation that has its own idempotency and retry semantics unrelated to the database's. The database transaction only ever records the outcome of a Git operation that has already completed, never brackets the operation itself.
- Made managed-mode invocation (`protocols/made-managed-mode.md`): the same trap applies to spawning and awaiting a `made validate --managed` process. That invocation can take an arbitrary amount of wall-clock time and must never happen from inside an open write transaction; the Gate row is written before the invocation starts (as `pending`, then `running`), the invocation runs entirely outside any transaction, and its result is written as a new short transaction once the process has exited.

**`busy_timeout`.** Set high enough that transient lock contention (for example, a checkpoint operation between the DatabaseWriter and a backup routine) resolves by waiting briefly rather than by surfacing `SQLITE_BUSY` to a caller. Because there is only one writer connection by construction, `busy_timeout` mostly matters for the interaction between the writer connection and any reader connection attempting a checkpoint at an inconvenient moment, not for writer-versus-writer contention, which the serialized write path already eliminates.

**WAL mode and an explicit checkpoint policy.** WAL mode is required so that readers are never blocked by the writer and vice versa. WAL mode alone does not eliminate the need for a checkpoint policy: without periodic checkpointing, the WAL file grows without bound, and read performance degrades as readers must scan an ever-larger WAL to find current values. The checkpoint policy runs on a schedule independent of any individual write, using a passive or truncate checkpoint mode chosen so it never blocks the single writer for an unbounded time.

**Foreign keys enabled.** SQLite does not enforce foreign key constraints by default; they must be turned on explicitly per connection. This is not optional here, because the relationships below (a Mission blocker referencing its Mission, an Attempt referencing its Mission, a Gate referencing its Mission) are exactly the kind of referential integrity a projections-as-truth model depends on to avoid orphaned rows silently accumulating.

**No long-lived read transactions.** A long-lived reader in WAL mode can prevent the WAL from being checkpointed, since SQLite cannot discard WAL frames that a still-open reader might need. Any read that could take an unbounded amount of time (for example, generating a large report) must not hold one open transaction for its duration; it should read in bounded batches instead.

**Event tailing polls by event ID.** Any consumer of the `domain_event` table that wants to react to new events (the EventBus, a MissionCoordinator catching up after a restart) does so by tracking the last event ID it has seen and querying for `id > last_seen_id`, never by holding an open transaction or a long-lived cursor. This keeps the read path compatible with the "no long-lived read transactions" rule above.

**Backup through SQLite's own mechanisms.** Backups are taken with `VACUUM INTO` or the SQLite backup API, never by copying the live database file directly. In WAL mode, the file that a naive `cp` would copy does not contain the full current state of the database; committed writes that have not yet been checkpointed back into the main file exist only in the separate WAL file alongside it. A backup that copies only the main database file, taken while the WAL file is non-empty, silently omits every write recorded in that WAL, producing a backup that looks complete but is missing an arbitrary amount of recent, committed data. `VACUUM INTO` and the backup API both read through SQLite's own consistent view of the database (main file plus WAL together), which is why they are the only acceptable backup mechanisms.

## Projections and their relationships

The following is a relationship summary, not a field-by-field schema; see the master architecture's domain model for full field lists.

**Project** is the root of ownership. Every Mission, Workspace, and the trusted Git mirror path belong to exactly one Project. Dispatch policy, validation policy, and integration policy are Project-level settings that lower-level entities inherit unless explicitly overridden at the Mission level.

**Mission** belongs to a Project and is the durable unit of authorized work. A Mission's `authorization_id` points at the Authorization row that granted it the right to run; `current_checkpoint_sha` and `current_delivery_sha` point at SHAs in the trusted mirror, never at anything workspace-local. A Mission's phase is a small enumerated set (draft, awaiting_authorization, authorized, active, and so on); a Mission does not encode every waiting condition as a phase, because waiting conditions are Mission blockers, not phases.

**Mission blocker** belongs to a Mission and references whatever it is blocked on through a polymorphic `subject_type`/`subject_id` pair (a Question, a Gate, an external dependency, and so on). A Mission's runnable state is derived, at read time, from its phase, its authorization, its open blockers, and current capacity; there is no separate "is runnable" flag to keep in sync, because a derived boolean that must be kept in sync is exactly the kind of state that drifts.

**Attempt** belongs to a Mission and represents one execution: a Soldier run, a scout, a reviewer, a repairer, or a validator. Its `workspace_id` points at the Workspace it used; its `retry_of_attempt_id` chains it to whatever Attempt it is retrying, if any; its `fencing_token` is what lets the daemon reject a stale Attempt's attempt to act after it has been superseded. Multiple Attempts can exist for one Mission over time, but the master architecture's Mission/Attempt distinction means only the Mission needs to survive any single Attempt being lost.

**Question** belongs to a Project and optionally to a Mission and an originating Attempt. `blocking_scope` distinguishes an Attempt-scoped Question, which is superseded automatically when its Attempt is superseded, from a Mission-scoped Question, which survives Attempt replacement and must be explicitly resolved or superseded at the Mission level. `request_id` is the deduplication key that makes an Attempt's retried acknowledgement request idempotent.

**Decision** belongs to a Question and records who answered it, through what channel, under what authority scope, and (for `sha_bound` and `mission_finding_waiver` scopes) what SHA or finding fingerprint it is valid for. A Decision's `expires_at`, `maximum_uses`, and `revoked_at` fields exist so that a waiver is never silently permanent or silently unbounded in how many times it applies.

**Gate** belongs to a Mission and represents one validation run at one `input_sha` against one `base_sha` under one `policy_hash`. `base_sha` was added to Gate identity because Made's own pipeline includes a rebase stage and diff-scoped review: a validation result for a given `input_sha` is only meaningful relative to the base it was diffed against, so the same `input_sha` re-evaluated after the base branch has moved is not the same Gate, even though the input commit itself is unchanged. A new Gate is created for every new `(input_sha, base_sha, policy_hash)` combination; it is never mutated in place to represent a rerun against a different SHA or base, because "the same Gate, but now pointing at a different SHA or base" would make it ambiguous which exact validation scope a stored result actually applies to.

**Mission validation ledger** belongs to a Mission and a gate type, and is the cumulative accounting (total runs, total repair rounds, identical-finding counts) that must survive across many Gates. This table exists specifically because Gate rows are per-SHA and must not be the place repair budgets live; if repair-round counting lived on the Gate row, creating a new Gate for a new SHA would silently reset the count, which is exactly the "new Gate does not reset repair accounting" invariant this table is built to satisfy.

**Authorization** belongs to a Mission and records a boss-granted permission (to work, to expand scope, to integrate, to perform a destructive operation, or to override policy), including who granted it, through what channel, and under what SHA/PR/ref scope. `consumed_at`, `expires_at`, and `revoked_at` exist so that an Authorization is never usable past the exact scope and time window it was granted for.

**Workspace** belongs to a Project and, while assigned, to a Mission. Its `lease_id` and `fencing_token` are the mechanism that lets the daemon distinguish the currently valid claim on a workspace from a stale one; its `last_known_clean` and `last_verified_at` fields record the Reconciler's most recent conclusion about whether the workspace is safe to reuse, per the reuse rules in `workspaces-and-git.md`.

**Artifact** belongs to a Project, optionally a Mission and an Attempt, and records a reference (path or URL) plus a content hash and the `input_sha` it was produced against, so that an artifact can always be tied back to the exact commit that produced it.

**External reference** maps an external system's identity (a Linear issue, a GitHub PR) to an internal entity, carrying a `sync_cursor` for whatever reconciliation process keeps it up to date. This table is what lets external side effects be reconciled by natural identity rather than assumed exactly-once, per the master architecture's outbox and reconciliation rules.

**Domain event** is an append-only audit record of what happened, keyed by `stream_type`/`stream_id`/`stream_version`. It exists for audit history and for the EventBus's polling-by-ID reactivity mechanism described above. It is explicitly not the source from which any projection is rehydrated; there is no event-replay subsystem, and no projection is ever reconstructed by replaying its event stream. If a projection and its event history ever disagree, the projection is correct and the event history is investigated as a possible instrumentation bug, not the other way around.

**Outbox item** represents one external side effect still pending or in flight, with `natural_key` and `idempotency_key` fields plus retry bookkeeping (`attempt_count`, `next_attempt_at`, `leased_until`, `last_error`). A local idempotency key alone is not sufficient for every external system (a GitHub PR creation, for example, needs to be reconciled by head branch, not just by a locally generated key, since the local key tells the local side nothing about whether GitHub already has a matching PR from a prior attempt that timed out after actually succeeding); this is why `natural_key` exists alongside `idempotency_key`, and why the outbox dispatcher's reconciliation logic is destination-specific rather than a single generic retry loop.

## Open questions flagged during drafting

- The exact WAL checkpoint schedule and mode (passive versus truncate, and on what interval or write-count trigger) is not chosen yet; this is a Phase 0 spike A concern (see the SQLite spike design) and should be settled with measured evidence rather than assumed here.
- Whether the Mission validation ledger is one row per Mission and gate type, or needs finer granularity (for example, per policy_hash, if policy can change mid-Mission) is not fully resolved; the master architecture's field list treats it as one row per Mission and gate type, and this document follows that, but a policy change mid-Mission is a case worth an explicit test.
- Poison-row quarantine (an invariant elsewhere in the master architecture: poison data quarantines one entity rather than restart-looping the daemon) is not given a concrete mechanism in this document; it needs to be specified as part of Spike A (SQLite) and likely involves a dead-letter-style table or status value that lets a malformed row be set aside without blocking the rest of the system's read/write path.
